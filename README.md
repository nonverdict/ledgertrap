# LedgerTrap — RL-среда для дообучения моделей финансового аудита

**Genesis Hackathon 2026, трек FinTech.** LedgerTrap — воспроизводимый симулятор для ИИ-аудитора.

**Что он делает:**
- генерирует вымышленную компанию за отчётный период: журнал проводок, счета, платежи, курсы валют, политику учёта;
- вносит в её книги настоящие аудиторские ошибки четырёх типов и корректные «ловушки», которые только выглядят как ошибки;
- даёт агенту узкие инструменты только для чтения;
- оценивает выводы агента по полям и доказательствам: награда из раздела 05 кейса.

**Чего в проекте нет:** это среда, а не обученная модель и не аудиторское заключение. Обучения весов нет. Наш `auditor` — скриптовая политика для демонстрации.

```
Конфиг + seed ─► ГЕНЕРАТОР ─► открытые файлы (manifest, ledger, invoices, payments, fx, policy)
                    │                        │
                    └─► truth + provenance   │   (только у оценщика)
                               │             ▼
 АГЕНТ (процесс) ◄─JSON─► СРЕДА reset/step ◄─ инструменты только для чтения
                               │
                      ОЦЕНЩИК (процесс): matcher + награда + журнал
 РЕ-АУДИТОР (без truth) ─► проверка эталона и сертификатов;  ОТЧЁТ: P/R/F1, возврат, шаги, время
```

## Одна команда проверки

Нужен только Python 3.11 (эталон — 3.11.18) и стандартная библиотека. Ставить ничего не нужно, сеть не нужна.

```bash
python3.11 -m ledgertrap check
```

**7 стадий, выход ≠ 0 при любом провале:**
1. все тесты (`unittest`);
2. побайтная регенерация 20 открытых эпизодов и сравнение с `episodes/`;
3. независимый ре-аудит 220 эпизодов против эталона;
4. базовые политики в режиме eval: агенты — отдельные процессы, оценщик — отдельный процесс;
5. статистический поиск утечек;
6. официальные проверки жюри через `judge_adapter.py`;
7. наши дополнительные проверки.

**Последний прогон:** `RESULT: PASS (11/11 checks passed)` примерно за 60 с на машине разработки. `--quick` — сокращённый вариант примерно за 12 с.

## Результаты (измерено, `reports/diagnostics.md`)

**Открытые выборки, режим eval** (P, R, F1 — микро; возврат = `clip(2·F1 − 1 − 0.002·шаги, −1, 1)`):

| Политика | train: возврат | train: F1 | train: шагов | dev: возврат | dev: F1 | dev: шагов |
|---|---|---|---|---|---|---|
| `oracle` (эталон, только у оценщика) | 1,000 | 1,00 | 0 | 1,000 | 1,00 | 0 |
| `auditor` (наш скрипт) | 0,967 | 1,00 | 16,5 | 0,940 | 1,00 | 29,8 |
| `naive` (простая сверка) | −0,895 | 0,07 | 16,5 | −0,846 | 0,11 | 29,8 |
| `random` (случайный, фикс. seed) | −1,000 | 0,00 | 75,7 | −0,435 | 0,00 | 57,9 |
| `flag_all` («пометить всё») | −1,000 | 0,00 | 16,5 | −1,000 | 0,00 | 29,8 |
| `silent` (пустой ответ) | −0,400 | — | 0 | −0,400 | — | 0 |

**Уровни сложности L1–L5** (по 30 сидов):

| | L1 | L2 | L3 | L4 | L5 |
|---|---|---|---|---|---|
| наш `auditor` | 0,985 | 0,977 | 0,965 | 0,941 | 0,902 |
| `naive` | −0,113 | −0,887 | −0,829 | −0,912 | −0,940 |

**Что ещё измерено:**
- **pass^k** на 5 перестановках ID и порядка: `auditor` 1,000 при k = 1…5, `naive` — 0.
- **Независимый ре-аудит:** 0 расхождений с эталоном.
- **Утечки:** по статистике внесённые записи не отличаются от чистых.
- **Время:** генерация эпизода — медиана 0,02 с; прогон аудитора — меньше 0,2 с (лимит 60 с).

**Как это читать.** `auditor` применяет те же опубликованные правила, что и ре-аудитор. Его F1 = 1 показывает, что задача решается по открытым записям, а не что что-то «обучилось». Отрицательный возврат `naive` и `flag_all` показывает, что ловушки и награда работают против простых трюков.

## Подключение жюри: `judge_adapter.py`

Файл лежит в корне (в контейнере — `/app/judge_adapter.py`). Запуск — из `/app`, например `python -c "import judge_adapter"`.

**`generate_episode(seed, config, output_dir)`** — наш генератор. Пишет:

```
output_dir/public/  manifest.json ledger.csv invoices.jsonl payments.jsonl fx.csv policy.json
output_dir/grader/  truth.json provenance.json certificates.json
```

- `config` — наш конфиг (см. ниже); `{"team_config": {...}}` тоже принимается.
- Секрет для HMAC-сида — переменная `LEDGERTRAP_SECRET`; по умолчанию открытый `ledgertrap-open-v1`.

**`make_env()`** → объект с `reset(seed, config)` и `step(action)`:
- **`reset(seed, {"mode": "closed", "episode_dir": D, "team_config": {...}})`** загружает папку `D` как есть: `public/` + `grader/` или все файлы прямо в `D`. Ничего не генерирует и не меняет ID. Награда — 0 на каждом шаге, `info = {}`.
- **`reset(seed, {"mode": "train", "team_config": {...}})`** генерирует эпизод по `seed`. Терминальная награда и агрегированные метрики возвращаются.
- **Первое наблюдение:** `{"task", "manifest", "policy", "remaining_steps": 100}`.
- **Действие:** `{"name": <имя>, "args": {...}}`:

  | Имя | Аргументы | Результат (`result`) |
  |---|---|---|
  | `list_records` | `table` ∈ `ledger`, `invoices`, `payments`, `fx`; `cursor` (`null` — первая страница); `limit` 1…50 | `{"records": [...], "next_cursor": str \| null}` — записи ровно как в файлах, в порядке файла |
  | `get_record` | `table`, `id`: ledger — `row_id`; invoices — `doc_id` или `invoice_id`; payments — `doc_id` или `payment_id`; fx — `YYYY-MM-DD:SRC:TGT` | объект записи |
  | `get_document` | `doc_id` | счёт (с `line_items`) или платёж |
  | `calculator` | `expression`: числа, `+ - * /`, скобки, ≤ 200 символов | десятичная строка, например `"0.3"` |
  | `submit` | `findings`: объект findings.json (§05) | `{"accepted": true}` или ошибка структуры `INVALID_SUBMISSION` |

- **Наблюдение после шага:** `{"result": ... | null, "error": null | {"code", "message"}, "remaining_steps": int}`.
- **Коды ошибок:** `BAD_ACTION`, `UNKNOWN_TOOL`, `BAD_ARGS`, `UNKNOWN_TABLE`, `UNKNOWN_ID`, `BAD_CURSOR`, `CALC_ERROR`, `INTERNAL_ERROR`, `EPISODE_DONE`, `STEP_LIMIT`, `TIME_LIMIT`. Сообщения — фиксированный текст, без ID, путей и данных.
- **Шаги и время:**
  - каждое действие, кроме `submit`, тратит шаг и входит в `inspection_steps`, ошибочные тоже;
  - `submit` — одно из 100 действий, но не шаг исследования;
  - 100 исследовательских действий → `truncated`, ответ пустой;
  - 60 с с начала `reset`, время политики включено → `truncated`, ответ пустой.

**`score_episode(episode_dir, findings, inspection_steps)`** → `{"tp", "fp", "fn", "precision", "recall", "f1", "return"}`:
- читает `truth.json` и открытые файлы папки;
- при неверной структуре `return = -1`, остальные поля `null`;
- причина пишется в `judge_adapter.JOURNAL`, а при заданной переменной `LEDGERTRAP_JOURNAL` — ещё и одной JSON-строкой в этот файл.

JSON-схемы: `schemas/judge_action`, `schemas/judge_observation`, `schemas/score_result`, `schemas/findings`.

**Соответствие четырёх типов ошибок кейсу (§02):**

| Тип ошибки в кейсе | `type` у нас | Варианты | `affected_ids` | Сумма и валюта |
|---|---|---|---|---|
| Дубли счетов | `duplicate_invoice` | `document` (второй документ), `double_posting` (счёт проведён дважды) | `doc_id` обоих счетов / `doc_id` счёта | итог дубля в валюте счёта |
| Пропущенное или частичное распределение платежа | `payment_allocation` | `missing`, `partial`, `wrong_invoice` | `doc_id` платежа и счёта X | нераспределённая на X часть в валюте платежа |
| Неверная дата или курс конвертации | `fx_conversion` | `wrong_date`, `wrong_rate` | `doc_id` документа | \|проведено − правильно\| в базовой валюте |
| Ошибка отнесения к периоду | `period_cutoff` | `early`, `late` | `doc_id` документа | сумма документа в его валюте |

Точные правила и шаблоны наборов доказательств агент видит в `policy.json` → `issue_types`.

**Настройки для закрытых эпизодов** (каждый тип включается отдельно) — `configs/scenarios/`:

| Сценарий | Конфиг |
|---|---|
| Чистые компании | `clean_basic`, `clean_split_payment`, `clean_refund`, `clean_repeated_amounts`, `clean_fx_period_boundary` |
| Ошибки по одной | `duplicate_document`, `duplicate_double_posting`, `allocation_missing`, `allocation_partial`, `allocation_wrong_invoice`, `fx_wrong_date`, `fx_wrong_rate`, `cutoff_early`, `cutoff_late` |
| Сцепленные сценарии | `c1_boundary_fx_partial`, `c2_duplicate_wrong_invoice` |

Любой параметр можно менять: например `{"errors": {"mode": "exact", "exact": {"fx_conversion:wrong_rate": 2, "C2": 1}}}`. Полная схема — `ledgertrap/config.py`; неизвестные ключи отклоняются.

## Как устроено

**Эпизод** — одна компания и один период: 200–2000 проводок, 20–200 документов, 0–12 ошибок.

**Форматы (§03):**
- время — ISO-8601 со смещением;
- деньги — целые минимальные единицы (KZT, USD, EUR, CNY, RUB, GBP — 2 знака, JPY — 0, KWD — 3);
- курсы — десятичные строки;
- пустая ссылка — `null` (в CSV — пустая ячейка, `manifest.csv_null = ""`).

**Мир компании:**
- базовая валюта KZT, USD или EUR;
- фиксированный часовой пояс;
- период [start, end) — месяц или квартал;
- окно после периода — 10 дней;
- три шаблона плана счетов, роли счетов перечислены в `policy.json`;
- курсы — только рабочие дни, берётся последний курс не позже локальной даты документа;
- округление `HALF_UP` или `HALF_EVEN`;
- гашение дебиторки накопительное по `invoice_refs`.

**Генератор** (`ledgertrap/generator.py`):
1. скрытая история;
2. чистые документы и проводки;
3. проверка бухгалтерских равенств I1–I11;
4. мутации с записью «было → стало» в `provenance.json`;
5. проверка, что видно ровно объявленное расхождение;
6. эталон и сертификат-расчёт на каждую ошибку;
7. выдача ID и порядка записей;
8. экспорт.

**Сцепленные сценарии:**
- **С1:** платёж в валюте на границе периода — по времени компании он уже в новом периоде, а в строке метки ещё последний день. Получаются две ошибки на одном платеже: период и курс.
- **С2:** дубль счёта, и платёж по оригиналу проведён на дубль. Две ошибки: дубль и распределение.

**Ловушки Л1–Л12** (корректно, но похоже на ошибку):
- регулярные счета на ту же сумму;
- одинаковые суммы у разных клиентов;
- разбитый платёж;
- кредит-нота и возврат;
- платёж в выходной по курсу пятницы;
- метка у границы периода в другом поясе;
- лаг проводки;
- аванс без ссылки;
- переплата;
- курсовые разницы;
- входящие остатки;
- законная частичная оплата.

**Ре-аудитор** (`ledgertrap/reaudit.py`) видит только открытые записи. Он должен:
- найти ровно эталон;
- подтвердить, что каждый набор доказательств сам по себе достаточен и минимален;
- подтвердить, что в книгах нет необъяснённых строк.

Иначе генератор сломан, и тест падает.

**Оценщик** (`ledgertrap/grader/`, открытый код):
- **структура:** −1 только за неверный тип значения, отсутствующее поле или превышенный лимит (30 выводов, 10 ID доказательств, 1000 символов);
- **сравнение:** ID, тип и валюта — точные строки; `affected_ids` и `evidence_ids` — множества;
- **допуск τ:** из `policy.json`, у нас 0 — каждую сумму можно пересчитать точно;
- **доказательства:** хотя бы один полный допустимый набор; несуществующий ID → вывод не засчитывается;
- **сопоставление:** максимальное паросочетание с детерминированным выбором;
- **метрики и награда:** точно по §05. Экспериментальная «мягкая» награда показывается отдельно и общую не заменяет.

## Свой агент

**Протокол:** JSON-строки через stdin/stdout.
- Раннер присылает `{"event": "reset" | "step", "observation": ...}`.
- Агент отвечает одной строкой-действием `{"tool": ..., "args": {...}}`.
- Агент работает отдельным процессом: пустая папка, минимальное окружение, без секрета.

```bash
python3.11 -m ledgertrap evaluate --config configs/dev.json --seeds 2000-2009 \
    --policy-cmd "python examples/minimal_agent.py"
```

`examples/minimal_agent.py` — 66 строк без импорта `ledgertrap`. На dev он получает возврат 0,200.

**Другие способы подключения:**
- `python3.11 -m ledgertrap serve --seed N` — среда как stdio-сервер: одна строка действия на вход, одна строка ответа на выход;
- `play` — то же для человека в терминале;
- для Python — класс `ledgertrap.env.LedgerTrapEnv` с `reset`/`step` в стиле Gymnasium, все значения JSON-совместимы.

## Воспроизводимость

**Сид и случайность:**
- внутренний сид = `HMAC-SHA256(secret, "ledgertrap/v1|seed|config_hash")`;
- свой ГПСЧ на SHA-256, без float и `random`;
- три независимых потока: сюжет, ID (`presentation.id_salt`), порядок (`presentation.order_seed`, `order`).

**Что гарантируется:**
- тот же seed, конфиг, версия и действия → побайтно те же файлы, наблюдения и награды, в том числе на другом `PYTHONHASHSEED` и в другом процессе.

**Версии:**
- generator 0.2.0, env 0.2.0, schema 1.1, config 1.0;
- версии записаны в `manifest.json` и `provenance.json`;
- у эпизода есть отпечаток открытых файлов.

**Выборки:** `configs/splits.json` (версия 1.0): train — сиды 1000–1009 (`configs/train.json`), dev — сиды 2000–2009 (`configs/dev.json`, другие сочетания параметров). Уровни сложности — `configs/presets/L1..L5.json`.

## Цикл улучшения аудитора (бонус, баллов не даёт)

Harness engineering на CPU, по образцу Harvey: диагностика на train → правка обвязки → замер на dev → проверка на свежих сидах. Весов нет.

| Версия | Что поменяли | train | dev | свежие 3000–3029 | шагов на dev |
|---|---|---|---|---|---|
| v0 | читает все таблицы, `get_document` по кандидатам в дубли | 0,9616 | 0,9330 | 0,9438 | 33,5 |
| v1 | без `get_document`: `list_records` уже отдаёт счета с позициями | 0,9670 | 0,9404 | 0,9491 | 29,8 |
| v2 | v1, а fx не читается, если в эпизоде одна валюта | 0,9670 | 0,9404 | 0,9491 | 29,8 |

- F1 = 1 у всех версий: прирост — только за счёт шагов.
- v2 помогает только эпизодам с одной валютой: на L1 0,9833 → 0,9853.

Полная таблица — `reports/diagnostics.md`, раздел 9. Дообучение модели на GPU (уровень 2 в плане) не делалось.

## Честные ограничения (Limitations)

Каждое ограничение можно проверить командой или файлом.

- **Задача упрощена.**
  - Только дебиторка: нет кредиторки, НДС, зарплаты.
  - Журнал в базовой валюте.
  - Пояса — фиксированные смещения, праздников нет.
  - Видно в `policy.json` любого эпизода.
- **Правила ошибок каноничны и опубликованы агенту.** Наш `auditor` использует те же правила, что и ре-аудитор (`ledgertrap/audit_rules.py`). Поэтому его F1 = 1 (отчёт, разделы 1–2) показывает решаемость, а не обучение. Реальные LLM-агенты в среде не прогонялись: нет платных API и GPU.
- **Синтетические данные.** Все компании, люди и деньги вымышлены; компания помечена «(вымышл.)» (проверка B20). Высокая награда не означает пригодности для реального аудита.
- **Изоляция — процессы, а не песочница.** Агент — отдельный процесс без секрета, с пустой папкой (проверки A19, C20), но под тем же пользователем ОС. Файлы открытых эпизодов на диске ему доступны — они и так открыты.
- **Docker проверен на одной машине разработки** (Docker 28.5, amd64): сборка и `docker run --network none --cpus 2 --memory 4g` проходят. На других архитектурах образ не проверялся.
- **Официальные проверки** прогоняются нашими сидами и нашим кодом по опубликованным определениям (`python -m ledgertrap jury`). Сиды жюри скрыты.
- **Свойства формулы кейса:**
  - молчание даёт −0,5 в среднем на смеси «5 чистых из 20» (`silent`: −0,400 на train);
  - усечение по шагам на чистой компании даёт 0,8 (проверка C16 в части 2).
- **Лишние существующие доказательства не штрафуются** — так в официальных определениях. Для `period_cutoff` после угадывания документа сумма и доказательства берутся из самого документа.
- **Обучения весов нет.** Об улучшении модели мы не заявляем. Таблица выше — улучшение скриптовой политики.

## Идеи, которые мы взяли (источники)

- **Контракт `reset`/`step`** — Gymnasium Env API: <https://gymnasium.farama.org/api/env/>.
- **Риски функции награды** (specification gaming), откуда атаки на награду в тестах — DeepMind: <https://deepmind.google/blog/specification-gaming-the-flip-side-of-ai-ingenuity/>.
- **Метрика pass^k, скрытое состояние и policy-документ для агента** — τ-bench: <https://arxiv.org/abs/2406.12045>.
- **Проверки, которые агент не может изменить, и честный выход вместо жульничества** — ImpossibleBench: <https://arxiv.org/abs/2510.20270>.
- **Свой эталон качества, ссылки на источник в каждом ответе, улучшение обвязки вместо модели** — Harvey (BigLaw Bench): <https://www.harvey.ai/en-US/blog/introducing-biglaw-bench>.
- **Среда как проверяемый пакет с наградой** — Prime Intellect Verifiers: <https://docs.primeintellect.ai/verifiers/environments>.
- **Наш прошлый проект:** своя копия проверок жюри после каждого изменения, тесты против независимого эталона, отдельный сид на каждый поток случайности.
