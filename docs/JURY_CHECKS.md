# JURY_CHECKS — проверки жюри и наши дополнительные проверки (v2.0)

> **Источник.** 20.11.2026 организаторы опубликовали официальные определения проверок FinTech:
> <https://genesis-exe.com/fintech-checks.html>. Часть 1 ниже — их проверки, пересказанные нашими словами, с
> указанием, где каждая исполняется у нас. Часть 2 — наши дополнительные проверки: они идут дальше по тем же
> критериям, но баллов не дают.
>
> ```bash
> python -m ledgertrap jury     # часть 1 (через judge_adapter.py), затем часть 2
> python -m ledgertrap check    # то же — стадии 6/7 и 7/7 общей проверки
> ```
>
> Код части 1 — `ledgertrap/official_checks.py`, часть 2 — `ledgertrap/jury_checks.py`. Отрицательные контроли
> (каждый блок обязан упасть, если вернуть сломанное поведение) — `tests/test_official.py`.

## Как жюри подключается: `judge_adapter.py`

Файл лежит в корне репозитория (рабочая папка в контейнере — `/app`). Три точки входа:

| Функция | Что делает у нас |
|---|---|
| `generate_episode(seed, config, output_dir)` | Наш генератор. Пишет `public/` (manifest, ledger, invoices, payments, fx, policy) и `grader/` (truth, provenance, certificates). `config` — наш конфиг, например `configs/scenarios/*.json`. Секрет для HMAC — переменная `LEDGERTRAP_SECRET`. |
| `make_env()` → `reset` / `step` | `reset(seed, {"mode": "closed", "episode_dir": ..., "team_config": ...})` загружает папку как есть: ничего не генерирует и не меняет ID; награда 0, `info = {}`. `mode: "train"` генерирует по `seed` и `team_config` и отдаёт агенту терминальную награду. Действие — `{"name", "args"}`. Наблюдение — `{"result", "error", "remaining_steps"}`; первое наблюдение — `{"task", "manifest", "policy", "remaining_steps": 100}`. |
| `score_episode(episode_dir, findings, inspection_steps)` | Оценка на стороне жюри: `{"tp", "fp", "fn", "precision", "recall", "f1", "return"}`. Неверная структура: `return = -1`, остальные поля `null`, причина пишется в журнал (`JOURNAL`, а при заданной `LEDGERTRAP_JOURNAL` — ещё и в файл). |

JSON-схемы: `schemas/judge_action`, `judge_observation`, `score_result`, `findings`.

Правила подсчёта шагов:
- `submit` входит в лимит 100 действий, но не в `inspection_steps`;
- любое другое действие, в том числе ошибочное, тратит шаг и входит в `inspection_steps`;
- после 100 исследовательских действий — `truncated`, ответ пустой;
- 60 с отсчитываются от начала `reset`, время политики включено.

## Часть 1. Официальные проверки (баллы)

Оценка: 25 · блок 1/20 + 25 · блок 2/20 + 25 · блок 3/20 + 15 · блок 4/20 + инженерия (до 10).

**Наши фикстуры:**
- **C** — чистый эпизод (`clean_basic`);
- **E** — эпизод с одной объявленной ошибкой (`duplicate_document`);
- **L** = C (в журнале не меньше 200 строк);
- **U** — ID, которого нет ни в одном файле; выбирается после чтения данных.

Сиды и секрет — наши (`jury-simulation-secret`): у жюри они скрыты.

### Блок 1. Контракт — 20 тестов (`block1`)

| ID | Что проверяется |
|---|---|
| C01 | `reset` возвращает пару; она и последующие обмены сериализуются в JSON |
| C02 | Первое наблюдение: задача, manifest, политика, остаток 100; нет seed, эталона, путей |
| C03 | В manifest есть обязательные поля; `counts` совпадают с файлами; правило округления совпадает с policy |
| C04 | `step` возвращает 5 значений; флаги — bool; всё сериализуется в JSON |
| C05 | Все четыре таблицы через `limit=50` и курсоры: страницы ≤ 50, без пропусков и повторов, порядок как в файлах |
| C06 | Один курсор дважды → те же записи в том же порядке; оба запроса тратят шаг |
| C07 | `get_record(R1)` = строка файла, без лишнего |
| C08 | `get_document(D1)` = документ файла |
| C09 | `0.1+0.2` → десятичная строка `0.3` |
| C10 | Файлы, `__import__`, `**`, `eval`, `;` в калькуляторе → контролируемая ошибка, ничего не исполняется |
| C11 | `get_record(U)` → ошибка, шаг потрачен, среда работает дальше |
| C12 | `get_document(U)` → ошибка, шаг потрачен, чужие документы не раскрываются |
| C13 | Неизвестное действие → ошибка, шаг потрачен |
| C14 | Допустимое → ошибочное → допустимое действие: бюджет уменьшается на 1 за каждое |
| C15 | После `submit`: `terminated`, журнал оценщика больше не меняется, дальнейшие действия → `EPISODE_DONE` |
| C16 | 99 исследовательских действий + `submit` сотым действием → принят, `inspection_steps = 99` |
| C17 | 100 исследовательских действий → `truncated`, ответ пустой, поздний `submit` не учитывается |
| C18 | Лимит 60 с: поддельные часы (политика «думала» 61 с) и реальные часы с лимитом 1 с → `truncated`, ответ пустой |
| C19 | Закрытый режим: награда — числовой 0 на каждом шаге, `info = {}`, итоговый ответ — только `{"accepted": true}`; истинная награда — у оценщика (`score_episode` и журнал) |
| C20 | На C и E пройдены все записи и документы; пробы `truth` / `../grader`, `shell`, `sql`, `http` → ошибка; в канале политики нет ключей эталона, provenance, seed, путей, секрета |

- **B01–B20** (часть 2): книги согласованы до внесения ошибок (откат мутаций из provenance); ре-аудитор без эталона находит ровно эталон; каждый набор доказательств достаточен и минимален; правила проводок соблюдены; нет необъяснённых строк; нет персональных данных;

- набор ошибок в эталоне ровно тот, что объявлен сценарием;
- в чистых эпизодах присутствует нужный отвлекающий случай.

### Блок 3. Сопоставление и награда — 20 тестов (`block3`)

**Фикстура:**
- эталон A: тип `duplicate_invoice`, R1, 10000 KZT, доказательства {D1, D2};
- B — вторая ошибка, для тестов 13–14;
- шагов по умолчанию 10, τ = 0.

| № | Вход | Ожидание (точность 1e-9) |
|---|---|---|
| N01 | Один верный вывод | 1/0/0, награда 0,98 |
| N02 | Пустой ответ | 0/0/1, −1 |
| N03 | Пустой эталон, пустой ответ | F1 = 1, 0,98 |
| N04 | Пустой эталон, ложный вывод | 0/1/0, −1 |
| N05 | Два одинаковых верных вывода | 1/1/0, F1 = 2/3, 47/150 |
| N06–N11 | Неверный тип / запись / сумма 10001 / валюта / только D1 / D1 + несуществующий ID | 0/1/1, −1 |
| N12 | Пять записей × четыре типа = 20 выводов | 1/19/0, F1 = 2/21, −871/1050 |
| N13 | Ошибки A и B, найдена только A | 1/0/1, 47/150 |
| N14 | A верно + один ложный вывод | 1/1/1, −0,02 |
| N15–N17 | 0 / 50 / 100 шагов | 1,0 / 0,90 / 0,80 |
| N18–N20 | 31 вывод / 11 ID доказательств / объяснение 1001 символ | −1, остальные поля `null` |

**Открытые примеры M01–M12** (`block3`, отдельная строка): повторы внутри списков, лишнее существующее доказательство, несуществующее доказательство, 11 элементов до удаления повторов, регистр и пробелы в валюте, отдельная фикстура с τ = 1 (граница включительно), сумма-строка и `true`, максимальное паросочетание (M10), детерминированный выбор пар (M11), повтор вывода (M12).

**Наш matcher (`ledgertrap/grader/`):**
- строки сравниваются точно;
- `affected_ids` и `evidence_ids` — множества после проверки лимитов;
- τ — из `policy.json` (`submission.amount_tolerance_minor`), у нас 0 для всех типов;
- ID доказательства обязан существовать: `row_id`, `doc_id`, `invoice_id`, `payment_id` или ключ fx `YYYY-MM-DD:SRC:TGT`;
- сопоставление — максимальное паросочетание; ошибки упорядочены по `issue_id`, у каждой — наименьший индекс вывода.

### Блок 4. Двадцать парных проверок (`block4`)

Жюри само меняет копию эпизода и подаёт её через `episode_dir`. Мы делаем так же (`transform`):
- **P01–P05** — перестановка записей всех таблиц;
- **P06–P10** — замена всех ID новыми, в других форматах (`row_0001`, `doc-0001`, `inv/0001`, `pay#0001`, `ent:0001`), во всех ссылках, в truth и provenance;
- **P11–P20** — и то и другое.

Порядок `line_items` и ключи fx не трогаются.

Пара засчитывается, только если выполнены все условия:
- повтор на исходном эпизоде точен, в том числе после `reset` в той же среде;
- ответ oracle с новыми ID после обратного перевода совпадает с исходным;
- TP/FP/FN/P/R/F1 и награда совпадают при тех же 3 шагах — и в `score_episode`, и в журнале среды;
- каждое доказательство достижимо через инструменты;
- записи отдаются в порядке файла;
- утечек нет.

## Часть 2. Наши дополнительные проверки (без баллов)
